## disk-monitor-alerts-20260922-20261022.ndjson.gz

`disk-monitor`'s alert log, 2,806 rows, 2026-09-22T17:52Z -> 2026-10-22T13:52Z,
copied out of `/tmp/disk-monitor-alerts.ndjson` on server4 (rotatable, unbacked).
md5 round-trip verified through the gzip. Found by `cluster`; the tool is theirs,
at `/home/ben/scripts/disk-monitor-cron`.

### Read `ssh_err` before counting anything

`host_unreachable` covers two unrelated failures:

| `ssh_err` | means |
|---|---|
| `FAIL df_rc=124` | `timeout 8 df -P /mnt/nas /` exceeded its bound on a host whose **ssh worked** — an NFS statfs stall. `df_rc` is only obtainable if the remote command ran. |
| `FAIL df_rc=255` | a genuine ssh failure. 743 rows, worker-only, a different phenomenon. |

Rows 1,166 · distinct timestamps 478 · distinct timestamps of `df_rc=124` **85**.
Only the last is the NFS signal. The first two read as a chronic daily condition
that does not exist.

`consecutive_fails` persists across ticks, so rows inside one episode are
correlated — count distinct timestamps, never rows.

### ⛔ `ts` IS A PER-CYCLE STAMP, NOT A PER-HOST PROBE TIME

This corrects the commit message of `d92354a`, which claims 36-49 hosts stalled
"in the same second". **That was timestamp granularity, not simultaneity.**

Measured: 696 distinct timestamps cluster at minutes 07/22/37/52 — the `*/15`
cadence — and **534 of 696 sit at second `:01`**. `disk-monitor-cron` has no
ThreadPool, no background `&` and no `xargs -P`, so the probe loop is SERIAL,
and 49 serial ssh probes cannot finish inside one second.

⭐ **PRECISION IS NOT RESOLUTION.** A field's format tells you the first; only
its writer tells you the second.

### ⛔ The arity argument is WEAKER than it looks — the monitor is PARALLEL

`disk-monitor.sh:144` is `probe_one "$name" "$ip" "$role" "$port" &` inside the
host loop, with a bare `wait` at `:146`. **~56 hosts are probed concurrently**,
and `TS` is set once at `:15`.

⇒ The 49 timeouts in a cycle ran **concurrently inside one ~8-12 s window**.
⇒ The statfs load in those cycles **is the monitor's own 56-way burst**, which
is exactly what `cluster`'s memo `0fee2412` says.

So the record **cannot separate "the NAS was stalling" from "56 concurrent
statfs calls caused the stall"**. What survives: 36-49 **distinct** clients
timing out rules out a single bad client path, and nothing more. The arity and
the fan-out are the same event.

⭐ **The independent samplers are the only evidence the stalls exist outside
the monitor's own activity** — `nfs-latency-probe` (fixed 2 s cadence, no
fan-out) and `cluster`'s `nas-write-tail-sample`.

### ⛔ FINDING THE STRING YOU EXPECT IN A PLAUSIBLE FILE IS NOT FINDING THE CODE THAT RAN

An earlier version of this file argued the opposite — a *serial* loop, therefore
49 x 8 s = **>= 6.5 minutes** of sustained stall. That inference is withdrawn.

It came from grepping `/home/ben/scripts/disk-monitor-cron`, which **is the alert
wrapper, not the writer**, and which contains a genuine reprobe copy of the
`timeout 8 df -P /mnt/nas /` payload. The grep found the expected string, found
no parallelism, and confirmed the hypothesis **in the wrong file**. There was no
error to notice.

The discriminator, which costs one command: `grep -n 'disk-monitor.sh'` in the
wrapper says at `:78` that `MON=~/.claude/skills/disk-monitor/disk-monitor.sh`
does the detection.

### Other limits, all cutting the same way

No latency field — an episode **indicator**, never pooled with a prober's
magnitude data. 8s bound, so blind below 8s. `*/15` cadence, so blind to
episodes shorter than the gap. `timeout` cannot interrupt a D-state stall, so
every row is a floor.
